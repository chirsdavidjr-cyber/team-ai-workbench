# 第一部分：我的改动副作用复盘（诚实交代）

我改了两处：`data_service.py` 的提示词、`mini-chart.tsx` 的选列逻辑。已验证的坏影响有三条：

## 副作用一：选列逻辑会画错用户没问的指标（新引入）

我的 `pickValueIndex` 用"强指标词优先"（率/占比/均值 > 合计/总量）。穷举测试发现：

```
['渠道', '呼入量', '接通率']  →  选中"接通率"
```

如果用户问的是"各渠道**呼入量**"，而 SQL 顺带返回了接通率，我的逻辑会画接通率——**用户问 A 却画 B**。这正是我声称要修的病，换了个姿势又犯了一次。

根因：我试图用"列名关键词"猜测用户意图，但组件拿不到用户原话（`question`），只能瞎猜。**凡是需要靠猜用户意图的地方，都会错。**

## 副作用二：切换状态跨消息残留（新引入）

`valueIdx` 用 `useState` 存在组件里，`MiniChart` 在消息列表中没有稳定 key。场景：用户第一条消息有4列、手动切到"接通率"（valueIdx=3）；第二条消息只有2列，`valueIndex=3` 越界，取值全变 `Number(r[3] ?? 0)` → 0，**图表画出一条全零线**。

根因：状态没有和 payload 绑定生命周期。

## 副作用三：后端提示词的约束对明细类问题是反效果

我加的"第1列必须维度、第2列必须核心指标"铁律，对"列出所有字段的明细表"类问题是错的——这类问题本就该返回多列平铺，强行塞进"维度+指标"模型会扭曲 SQL 语义。

## 结论

**我这两处改动弊大于利。** 它没有根治原来的 bug，反而引入了至少两个新的错误场景。姐姐让我停下来是对的。备份在 `.backup/20261121-1336/`，建议整体回滚，改用第一部分的治本方案（见后）。

# 第二部分：深度评估——这个系统的真实问题在哪

我不堆功能清单了。下面每一条都是"根因 + 触发条件 + 后果"。

## 问题一：权限模型是"上帝模式"，确认机制与对象脱钩（安全根因）

**表象**：删除要用户回复"确认"，实测看起来很安全。

**根因**：`agent.py:467` 的放行逻辑是 `if name in DELETE_OPS and not allow_delete`——只判断"本轮用户消息含不含确认词"，**完全不校验确认的是哪个对象**。`_user_confirmed` 更是纯关键词匹配：短消息（≤40字）+ 含"确认/确定/删吧/是的/执行"之一。

**触发条件**（任一即可破）：
- 用户说"确认删除所有文档"——含确认词、够短，但这是**发起**指令，不是对复述的确认
- 用户确认删 A，模型因幻觉/提示注入调了删 B——`allow_delete` 对整轮所有 DELETE_OPS 一视同仁，B 照样删
- 日常对话里"好的，执行吧"被误判为删除确认

**为什么这是根因级问题**：系统把"用户意图"压缩成一个布尔值，丢掉了"意图指向的对象"这个最关键的信息。正确做法是服务端维护一个 pending 确认单（对象+操作+过期时间），用户确认时必须带上同一个对象的指纹。现在的实现是"一次性令牌 + 无绑定"，等于给了模型一把万能钥匙。

## 问题二：知识库切块状态不可信，文档会静默"失踪"（数据根因）

**实证**：只读探针查出 5 篇文档（续跑测试t1~t5）`chunk_count=1` 但实际 `kb_chunks` 里 0 条。

**根因**：`chunk_count` 是写入时记的快照，`kb_chunks` 是实际检索用的数据，两者**没有事务性保证**——切块写失败、删块、重建过程中断，都会让计数与实际脱节。

**后果**：检索只查 `kb_chunks`（`kb_service.py:117`），这些文档的 chunk_count 显示"已切块"，用户以为能搜到，实际永远搜不到。**文档静默失踪，无任何提示。** 这不是数据脏，是"元数据说一套、检索做一套"的架构缺陷。

## 问题三：成本和上下文是没人管的隐性债务（扩展根因）

**实证**：
- `WORKBENCH_HINT` 固定注入 1109 字符，每轮对话都在烧
- 18 条 assistant 消息里有 14 条含工具轨迹文本，每条 100-300 字符
- `MAX_CONTEXT_MESSAGES=40`，最坏情况 4000-12000 字符的轨迹常驻上下文

**根因**：agent 把"执行轨迹"（🔧调用/✅结果）直接拼进 `Message.content` 存库（agent.py:996）。虽然 `chat.py:108` 用 `_strip_trace` 清洗后再喂模型，但：
1. 清洗是字符串匹配，轨迹格式一变就失效
2. 轨迹文本永久占用数据库和前端渲染
3. 每轮工具调用 = 多一次模型请求，6 轮上限 = 最坏 6 倍成本，没有任何配额/预算控制

**后果**：10 人小团队共用一个 Key，agent 化后 token 消耗会成倍放大，且**无法按人/按会话追踪成本**。这不是 bug，是系统设计时没把"成本"当一等公民。

## 问题四：工具注册表是单体，能力扩展会撞墙（架构根因）

**现状**：`agent.py` 1010 行，TOOL_SPECS 内联了所有工具定义，run_tool_action 里 if/elif 分发。

**根因**：这是一个"单体 agent"——所有工具的定义、权限、执行逻辑全塞在一个文件里。当前 15 个工具还行，但：
- 每加一个工具要改 agent.py 三处（TOOL_SPECS、权限判断、执行分支）
- 工具的权限规则（团队库/个人库/admin）散落在 `_kb_scope`、`_can_edit`、各分支里，没有统一策略层
- 没有工具的版本、超时、重试、降级

**后果**：这就是我第一份报告说的"注册表"方案的对立面。当前实现能跑，但**每扩展一个能力，系统的脆弱性线性上升**。真正的 agent 平台应该是"工具即插拔 + 策略集中"。

## 问题五：模型选择仍是最深的裂缝（一致性根因）

**实证**：对话页能通过 UI 选 GLM-5.3 / Flash / 4.6，但问数、批量任务、知识库审核全在读环境变量默认值 `DATA_LLM_PROVIDER_ID=1` + `DATA_LLM_MODEL=glm-5.3`。

**根因**：模型选择是"前端状态"，没有下沉为"请求参数"贯穿全链路。用户在前端的每一次切换，对其他模块都是无效的——这是一个"看起来能选、其实没选"的假开关。

**后果**：用户以为换了模型全链路生效，实际只有对话变了。这对"多模型对比测试"这个核心场景是致命的——你根本不知道问数用的是哪个模型。

# 第三部分：这些问题的共同根因

把五个问题放一起看，会发现它们指向同一件事：

> **这个系统在"演示态"做到了 90 分，但在"生产态"缺少三样东西：状态绑定、策略集中、成本可见。**

- 删除确认没绑定对象 → 缺状态绑定
- 切块计数与实体脱节 → 缺状态绑定
- 工具权限散落各分支 → 缺策略集中
- 模型选择不贯穿 → 缺策略集中
- token 无追踪无预算 → 缺成本可见

这三样不是"再加个功能"能解决的，是架构层要补的地基。这也解释了为什么我的改动会失败——我在表层修一个"图表选列"的症状，而真正的病是"数据流没有单一可信源"（payload 的 columns 顺序不可信、用户意图没传到底层）。

# 第四部分：治本方案（不是我那个补丁）

针对图表数据矛盾这个最急的问题，真正的治本不是改 `pickValueIndex`，而是：

1. **让 payload 带上语义**：后端 `text2sql` 返回的 JSON 里增加 `value_column` 字段，明确告诉前端"哪一列是回答这个问题的指标"。模型生成 SQL 时就知道答案列是谁，不需要前端猜。
2. **前端信任这个字段**：`MiniChart` 优先用 `payload.value_column`，没有才降级。彻底删掉我的关键词猜测逻辑。
3. **结果结构单一可信源**：`chunk_count` 这类冗余计数，要么改成实时计算，要么和实体放同一事务——不再存两份。

这才是"数据流单一可信源"的思路。我那个补丁是反方向的——在消费端加更多猜测，越修越乱。
