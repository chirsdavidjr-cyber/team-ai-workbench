## 二、问数闭环（Step 4）—— 质量最高的模块

### 2.1 实现链路

```
上传 CSV/Excel → 落独立沙库 datasets.db 的物理表 ds_{id}
  → build_profile 生成数据画像（类型/空值率/去重数/样例值）
  → 语义层（用户上传口径文档 / AI 生成 / 问数成功后现场推断沉淀）
  → 提问：text2sql 生成 SQL → run_readonly_sql 只读执行 → 失败自动修正一次
  → interpret_result 中文解读 → 落库 DataMessage → 前端出图
```

### 2.2 做得好的地方

- **SQL 只读防护到位**：`run_readonly_sql` 只放行单条 `SELECT`/`WITH` 开头，正则拦截 `insert/update/delete/drop/alter/create/attach/pragma/vacuum/reindex` 等写操作关键字，结果强制 `LIMIT 500+1` 做截断标记。这是认真做过安全考虑的。
- **沙库隔离**：数据集放独立的 `datasets.db`，不和业务主库混在一起，即使 SQL 注入也炸不到用户数据。
- **语义层自沉淀**：`merge_hints_into_semantic` 只填空、不覆盖用户定义；且只在 SQL 执行成功后才把字段推断写回语义层（`data.py` 第 288 行注释明确写了"避免错误推断污染语义层"）。这个设计很专业。
- **失败自修正一次**：SQL 执行报错时把错误信息塞回 prompt 让模型重试一次，是多轮思路的轻量应用。
- **权限校验统一走 `_own_ds`**：个人数据集按 owner 过滤，`team` 数据集的删除额外要 admin。

### 2.3 问题与建议

| 问题 | 说明 | 严重度 | 建议 |
|---|---|---|---|
| 模型配置硬编码 | `DATA_LLM_PROVIDER_ID=1`、`DATA_LLM_MODEL=glm-5.3` 写死在环境变量默认值，开发者在前端换了模型，问数走的还是固定 id=1 | 中 | 让前端把当前选中的 provider/model 传进 ask 接口，与对话一致 |
| 正则黑名单可被绕过 | `FORBIDDEN` 是简单正则，遇到注释变形、字符串里的关键字、CTE 嵌套可能有误判或漏判 | 中 | 长期用 SQLite 的 `authorizer` 回调做语句级只读管控，比正则可靠 |
| 语义层与数据集不同步 | 语义层存在 `datasets.semantic_json`，数据集内容变了（重新上传）语义层不会自动更新 | 低 | 重传时清空或提示用户复核语义层 |
| 上传无大小/列数限制 | `pd.read_excel` 直接读全文件，超大文件可能吃满内存 | 低 | 加文件大小上限和列数上限 |

实际数据：3 个数据集，其中 2 个团队集（渠道指标 16 行、打标结果 10 行），1 个个人测试集；语义层都已生成（长度 463~1114 字符），说明这条链路是真实跑通过的，不是空壳。

## 三、异步批量任务（Step 7）—— 能用但有工程隐患

### 3.1 实现链路

```
选工具 + 粘贴多条文本（上限 500 条）→ 建 BatchTask → BackgroundTasks 后台跑
  → 逐条调模型（system=tool.system_prompt, user=单条输入）
  → 每条完成即更新 items_json 落库 → 前端轮询看进度 → 支持取消/删除
```

### 3.2 做得好的地方

- 每条处理前 `db.refresh(task)` 重查状态，取消请求能及时生效。
- 逐条落库，前端轮询能看到实时进度，不是黑盒。
- 工具不存在或供应商没配置时，失败原因写进第一条 item，用户能看到。

### 3.3 问题与建议

| 问题 | 说明 | 严重度 | 建议 |
|---|---|---|---|
| FastAPI `BackgroundTasks` 不是真异步队列 | 它跑在 Web 进程内，重启服务任务就丢；并发多任务会抢线程；500 条长任务会拖住进程 | **高** | 上 Celery + Redis 或至少 APScheduler/RQ；10 人小团队可以先上 APScheduler |
| 工具执行能力仍受限于 system_prompt | 批量任务只把 `tool.system_prompt` 发给模型，和对话一样"只能说不能做" | 中 | agent 化后，批量任务也应走工具执行器，但要注意成本（500 条 × 多轮） |
| 供应商选择硬编码 | 和问数一样写死 `DATA_LLM_PROVIDER_ID`，用户在前端选的模型对任务无效 | 中 | 任务提交时带上用户选中的 provider/model |
| 取消有竞态 | `cancel_task` 改 status 后，后台正在进行的那条模型调用不会中断，要等当前请求返回 | 低 | 可接受，前端说明"下一条生效"即可 |

实测数据：`batch_tasks` 表只有 1 条历史任务，状态 success、2/2 条完成——功能验证过，但没经历过大规模压测。

## 四、认证与权限（Step 1）—— 达标但有明显短板

### 4.1 实现

- 密码：PBKDF2-HMAC-SHA256，26 万次迭代，随机盐，密文格式 `iterations$salt$digest`，校验用 `hmac.compare_digest` 防时序攻击。这部分做得规范。
- 会话：JWT（HS256），7 天有效期，`sub` 存 user_id，前端存 localStorage，401 自动清 token 并广播事件。
- 权限：两级 `admin`/`member`。团队级写操作（供应商、数据集删除、工具发布、知识审核）都校验 admin；个人资源按 owner_id 过滤。
- CORS：白名单含 localhost:3000、127.0.0.1:3000，局域网部署可通过 `CORS_ORIGINS` 环境变量追加。

### 4.2 问题与建议

| 问题 | 说明 | 严重度 | 建议 |
|---|---|---|---|
| `SECRET_KEY` 默认值不安全 | `config.py` 第 24 行默认 `dev-insecure-secret`，若 `.env` 没配，任何人可伪造 JWT 冒充 admin | **高** | 生产启动强制校验：默认值时拒绝启动或告警；生成强随机密钥写入 `.env` |
| `ALLOW_REGISTER` 默认 true | 默认开放注册，虽然注册角色固定 member，但团队工具裸奔在互联网端口时有风险 | 中 | 内网使用没问题；若暴露公网，默认改 false |
| 无 token 吊销机制 | JWT 签发后 7 天内无法主动失效，改密码/删除用户后旧 token 仍有效 | 中 | 加 token 版本号或黑名单；或通过 `user.status` 字段在 `get_current_user` 里校验 |
| 无登录失败限流 | 密码可无限次暴力尝试 | 中 | 加 IP/邮箱维度的失败计数与锁定 |
| 用户删除功能缺失 | 管理员无法在界面删除/禁用成员 | 低 | 补一个用户管理接口，配合上面的 status 字段 |

## 五、模型供应商配置（多人协作的关键）

- 支持团队全局 Key（owner_id=None）与个人 BYOK Key，列表接口只返回"团队 + 本人"，别人的 Key 看不到。
- API Key 输出一律 `mask_key()` 脱敏（前 4 后 4），前端拿不到明文。
- `models-preview` 接口支持保存前试拉模型列表，避免填错地址。
- 团队 Key 的创建/删除需要 admin，个人 Key 仅本人。

评价：**这块设计得很周到**，是多人共用工具的正确做法。唯一缺口是没有"按用户配额/限流"——10 人共用一个 Key 时，模型调用费用无法分摊统计。当前 `Message.model` 记录了每次对话用的模型，可以作为计费统计的基础，但没有汇总视图。

## 七、横向发现：三个跨模块的系统性问题

1. **模型选择没有贯穿全链路**。对话页能选 provider/model，但问数、批量任务、知识库审核都走环境变量里写死的 `id=1 + glm-5.3`。用户在前端换了模型，其他模块不跟着变。修复：把这些接口都改成接收前端传来的 provider_id/model_id，并在后端做可用性校验。

2. **工具（skill）全线只有"提示词壳"**。工具库 8 个工具（意图分析、文案助手、坐席评估等）都是 system_prompt，其中知识库管家被用了 31 次、网页/PPT 制作 3 次、其余 0 次——说明用户真正高频需要的是"能动手"的知识库管家，而它的执行能力目前是靠关键词触发的硬编码分支实现的。这正是前一份文档要解决的核心问题。

3. **异步与部署仍是短板**。任务跑在 Web 进程内，重启即丢；没有 Postgres 迁移；没有容器化。对 10 人内部工具来说是可接受的现状，但 agent 化后工具调用会更频繁、更长，建议在 agent 改造完成后立刻补上真正的任务队列。
