# 通用需求处理

用户提出默认场景之外的采集需求时按本文件处理。目标：把模糊需求变成可执行配方，不逐项挤牙膏式提问。

## 需求解析清单

从用户话里提取六项：

1. 主题：要采什么（如"新能源车险""医保谈判"）
2. 站点范围：指定站点还是自动匹配
3. 关键词：用户给的明确词
4. 时间范围：近几天/某时间段/不限
5. 字段：要哪些字段（默认全字段）
6. 数量：条数上限

用户没说的用默认值：站点自动匹配、时间近 30 天、字段全量、单站 ≤200 条。只有站点和关键词确实无法确定时才问，一次问完。

## 站点映射

按主题把关键词归入 `keyword-bank.md` 的六节之一，然后：

- 命中行业/监管/同业/险种/医药医保 → 用 `site-registry.md` 对应站点
- 用户指定新站点 → 先 WebFetch 实测可达性，确认无需登录，再登记进站点台账
- 没有对应站点 → 向用户说明现状，建议相近站点或让用户提供网址

## 需求分流

| 用户要求 | 处理 |
| --- | --- |
| 公开网页采集 | 正常执行 |
| 需要登录的平台内容 | 拒绝该部分，说明本 skill 只做公开网页，保留公开可做部分 |
| 实时/高频监控 | 说明公开采集的时效边界，建议定时批次 |
| 含个人信息的定向采集 | 拒绝，说明隐私边界 |
| 只要标题不要正文 | 按用户要求，但台账里标注"仅标题" |
| 要完整正文 | 默认行为，列表取链接后逐条抓详情 |

## 配方确认

执行前把配方用一两句话复述给用户：采哪些站点、用什么关键词、多少条、时间范围。用户说"就这么办"或没异议就开跑。简单明确的需求（如"帮我采一下最近的医保政策"）可直接跑，不必复述确认。

## 多需求并存

用户一次给多个需求时：

1. 拆成独立批次，每批一个方向。
2. 共用一份总台账，各自明细与配方。
3. 最后给一张跨批次汇总表。

## 需求变更

采到一半用户改需求：当前批次跑完不中断，新需求另起批次，不混在同一批里改配方。
