# 数据库（问数）模块：可操作性 / 实用性 / 交互性评估与改善方案

> 评估对象：`/data` 数据集列表页、`/data/[id]` 问数详情页、图表组件、后端 `data.py` + `data_service.py`
> 评估维度：可操作性（能不能顺手把活干了）、实用性（解决真问题的程度）、交互性（人机对话的顺畅度）
> 评估方式：静态代码审阅 + SQLite 只读查询，未修改任何代码与数据
> 评估日期：2026-11-21

---

## 一、总体结论

这个模块的基本盘很扎实：**上传 → 看数据 → 建语义层 → 自然语言问数 → 出图出 SQL**，五步闭环全通，而且 SQL 只读防护、沙库隔离、语义层自沉淀这些硬骨头都啃下来了。它不是 demo，是能干活的东西。

但这三个维度的发展不均衡：

| 维度 | 评分 | 一句话 |
|---|---|---|
| 可操作性 | 中上 | 主流程顺，但"问完拿走"和"结果复用"两个出口没打通 |
| 实用性 | 高 | 语义层自沉淀是真正的亮点，用得越久越准 |
| 交互性 | 偏弱 | 非流式、不能取消、图表写死前两列，是三大体验短板 |

最该改的四件事：**问数改流式 + 结果可导出 + 图表支持用户手动改配置 + 补充追问上下文**。下面逐项说。

## 二、可操作性评估

### 2.1 做得好的

- **上传即导入、导入即引导**：拖拽上传到列表页，成功后直接跳到详情页并打开"数据预览"tab（`data/page.tsx` 第 56 行），让用户先看清楚自己的数据再问数。这个跳转设计很懂用户。
- **四个 tab 分工清楚**：问数 / 数据预览 / 数据画像 / 语义层，各司其职，顶部切换，不用来回跳页。
- **语义层三种来源齐备**：上传口径文档自动解析、问数成功时 AI 现场推断沉淀、手工逐字段编辑。而且明确写了"手工定义不会被 AI 覆盖"（`merge_hints_into_semantic` 只填空不覆盖），用户信任感有保障。
- **字段多时可过滤**：超过 8 个字段才出现过滤框，避免小表噪音、大表好找。
- **SQL 全程透明**：每条回答都能展开看 SQL，业务人员可以核对口径，这是问数工具建立信任的关键设计。
- **历史可复用**：对话记录落库，用户消息可点击重新提问（`data/[id]/page.tsx` 第 225 行）。

### 2.2 问题清单

| 问题 | 现象 | 影响 | 严重度 |
|---|---|---|---|
| 结果无法导出 | 全项目搜不到任何 download/blob/导出逻辑，图表和表格只能看不能拿走 | 用户问完数还得手动抄进 Excel，实用性大打折扣 | **高** |
| 问数不能取消 | `ask()` 用普通 `api()` 一次性等待，没有 AbortController；模型慢或 SQL 卡住时只能干等，连 busy 状态都解不开 | 一次失败的等待会卡住整个页面 | **高** |
| 问数非流式 | 对话（chat）是 SSE 逐字输出，问数却是黑盒等待，只显示"正在生成 SQL 并执行…"的转圈 | 体感差距明显，几秒的等待像卡死 | **高** |
| 无多数据集关联 | 一次只能对一个数据集问数，跨表 join 做不到 | 业务问题常跨表，能力天花板低 | 中 |
| 数据预览只能看前 50 行 | 上限 200，且提示"完整数据请用问数查询"，但问数结果也只能看前 15/500 行 | 想核对原始数据很不方便 | 中 |
| 没有快速重传/更新 | 数据集上传后不能替换数据（只能删了重传，问数记录一并丢失） | 月度报表更新场景很痛 | 中 |
| 问数记录无法删除单条 | 只能删整个数据集连带清空 | 误问、敏感问题无法单独清理 | 低 |
| 预置问题写死 | 三个开场问题是通用模板（"各渠道接通率是多少"），不随数据集变化 | 换到"打标结果"数据集，这些问题驴唇不对马嘴 | 低 |

## 三、实用性评估

### 3.1 真正的亮点：语义层自沉淀机制

这是整个模块最有价值的设计，值得单独讲清楚：

1. 用户上传数据集 → 画像自动生成（字段类型、空值率、唯一值、样本值）。
2. 语义层可以从口径文档导入、AI 生成草稿、或手工填写。
3. 用户问数时，模型会顺带返回 `semantic_hints`——对它认为是新字段的现场业务含义推断。
4. **只有 SQL 执行成功后**，`merge_hints_into_semantic` 才把这些推断写回语义层，且只填空、不覆盖用户已定义的。

实测数据佐证：3 个数据集的语义层分别有 803、1114、463 字符的定义，都在 ready 状态——这条链路是真实跑通的。

这个机制的实用价值在于：**问数准确率会随着使用自我进化**。用户不用一次把所有字段口径写完，先用起来，模型边用边补，用户偶尔校正。这比"必须先建好完美的语义层才能问数"的设计实际得多。

### 3.2 其他实用性优点

- **SQL 只读 + 独立沙库**：`run_readonly_sql` 拦截写操作关键字，数据在 `datasets.db` 与主业务库隔离。安全底线守住了。
- **失败自修正一次**：SQL 报错时把错误信息回灌模型重试一次，多数小语法问题能自愈。
- **图表类型模型自选**：line/bar/pie/table 由模型按数据形态判断，自动化程度高。
- **口径可追溯**：AI 解读 + SQL 展开 + 引用数据预览，业务人员能核对结论怎么来的。

### 3.3 实用性问题

| 问题 | 说明 | 严重度 |
|---|---|---|
| 模型配置硬编码 | 问数写死用 `id=1 + glm-5.3`，用户在前端切换了模型不生效 | 中 |
| 数据时效性无标注 | 数据集没有"数据截止日期/更新时间"展示，问"本月数据"时用户不知道库里是几月的 | 中 |
| 无查询频率/热度统计 | 不知道哪些问题被反复问，无法沉淀为常用报表 | 低 |
| 无异常数据提示 | 画像算出了空值率、唯一值，但没有主动提示"某字段 80% 为空，问数结果可能不可靠" | 低 |

## 四、交互性评估

### 4.1 交互优点

- 输入即问、回车即发，零学习成本。
- 空状态给了三个可点的示例问题，引导清晰。
- 用户消息点击可重问，符合"改个词再试"的真实使用习惯。
- 语义层枚举翻译用 `key=value, key=value` 的纯文本输入（失焦解析），比让用户填 JSON 友好得多。
- AI 解读用浅色卡片 + "AI 解读"标签，视觉层级清楚。
- 主题切换、折叠侧栏等偏好持久化。

### 4.2 交互问题

| 问题 | 现象 | 影响 | 严重度 |
|---|---|---|---|
| 非流式等待 | 问数走 `api()` 一次性返回，等待期间只有一个转圈 | 体感卡死，无法判断是慢还是挂了 | **高** |
| 图表写死前两列 | `MiniChart` 约定第 1 列标签、第 2 列数值（第 10-20 行），三列以上的结果直接被忽略 | 模型选了 table 还行，选了 bar/pie 时数据展示不全 | **高** |
| 图表不可切换 | 用户无法手动把 bar 改成 line，也不能选哪列做维度、哪列做数值 | 模型判断错了用户没法纠正 | **高** |
| 表格结果只显示 15 行 | 问数结果 `rows.slice(0,15)`，无分页无展开，且不能导出 | 稍大一点的结果集看不全 | 中 |
| 无进度细分 | 只显示"正在生成 SQL 并执行…"，不区分"生成 SQL / 执行中 / 写解读" | 用户不知道卡在哪一步 | 中 |
| 错误信息生硬 | 失败时红框直接甩后端 `error` 字符串（往往是模型原始报错），无引导 | 业务人员看不懂，不知道下一步怎么办 | 中 |
| 追问无上下文 | 每轮问数独立，问"那环比呢"模型不知道"那"指什么 | 无法连续分析，每次都要把上下文说全 | 中 |
| 数据预览与问数割裂 | 预览在看数据、问数在另一个 tab，不能"选中某列直接问" | 少了最自然的交互入口 | 低 |

## 五、改善方案（按优先级）

### P0 一是让结果拿得走：导出功能

**前端**：在每条 AI 回答的操作区加"导出 CSV"按钮，把 `payload.columns` + `payload.rows` 用 `Blob` + `URL.createObjectURL` 生成下载；SQL 加"复制"按钮。

```tsx
function exportCsv(payload: ChartPayload) {
  const esc = (v: unknown) => `"${String(v ?? "").replace(/"/g, '""')}"`;
  const csv = [payload.columns.map(esc).join(","),
    ...payload.rows.map(r => r.map(esc).join(","))].join("\n");
  const url = URL.createObjectURL(new Blob(["\uFEFF" + csv], { type: "text/csv" }));
  const a = document.createElement("a");
  a.href = url; a.download = `${payload.title || "查询结果"}.csv`; a.click();
  URL.revokeObjectURL(url);
}
```

加 `\uFEFF` BOM 是为了 Excel 打开中文不乱码。这是投入最小、体感提升最大的一步。

### P0 二是问数改流式 + 可取消

**后端**：`/ask` 改成 SSE，分阶段推事件：`stage`（生成 SQL / 执行中 / 解读中）、`sql`（生成即推）、`chart`（结果出来即推）、`interpret`（解读逐字）、`done`。

**前端**：从 `api()` 换成类似 `streamChat` 的流式读取，加 `AbortController`，忙时显示"取消"按钮，`abort()` 即中断请求并解锁 busy 状态。

这样用户能立刻看到 SQL 在生成，等待从"黑盒"变"可见过程"，和对话页体验对齐。

### P0 三是图表可配置

**前端**：给 `MiniChart` 加一个"配置"入口，让用户选：
- 维度列（默认第 0 列）
- 数值列（默认第 1 列，可改成其他数值列）
- 图表类型（bar / line / pie / table 手动切换）

配置只影响展示、不改 `payload` 数据，纯前端状态即可。这样模型选错了用户一键纠正，多数值列也不再被埋没。

### P1 四是结果分页与展开

- 表格结果从 15 行提到 50 行 + "展开全部"按钮（最多 500 行，与后端截断上限对齐）。
- 数据预览支持按列排序、输入行数上限调到 200（后端已支持），让"核对原始数据"这条路真正可用。

### P1 五是补充追问上下文

- 把最近 N 轮问数的「问题 + SQL + 结论摘要」塞进 `text2sql` 的 system/user prompt，让"那环比呢""换个维度"这类追问成立。
- 前端保留追问输入的历史引用提示（如"基于上一个问题"）。

### P1 六是数据集可更新

- 增加"替换数据"接口：上传新文件覆盖 `ds_{id}` 表、更新画像和行数，但**保留问数记录和语义层**（语义层字段若变化则标记待复核）。
- 这样月度报表更新不用删库重建。

### P1 七是模型选择贯穿

- `/ask` 接口接收前端当前选中的 provider_id / model_id（与对话页一致），去掉 `data_service.py` 里硬编码的 `DATA_LLM_PROVIDER_ID` / `DATA_LLM_MODEL` 默认值依赖。

### P2 八是体验细节

- 预置问题改为**按数据集画像动态生成**（如取 `profile` 里的数值列名拼问题），替代写死的三句。
- 错误信息做友好化映射：模型超时、SQL 语法错、无结果分别给不同的中文提示和"试试这样做"建议。
- 画像页加数据质量提示（空值率 > 30%、唯一值 = 1 等异常自动标黄）。
- 数据集加"数据截止日期"字段，问数结果里带上，避免时效误判。
